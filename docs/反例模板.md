# 反例模板（Agent 行为冗余 / 返工清单）

用途：记录「我已经犯过一次的错」，供后续同类任务直接查表，避免重复消耗 token 与返工。
原则：**反例只记真实发生过的错**，不记假想风险；每条必须写清「触发条件 → 判错信号 → 正确做法」。
状态标记：`待修` = 已发生、尚未在系统里固化；`已固化` = 已有脚本/命令/检查项兜住。

最近补录：2026-10-05（反例 6 防御性重复验证 + 核验预算表，用户原话「还不要在阅读文献的过程中过多地重复验证、防御性阅读」）。

---

## 条目格式

```
### 反例 N — 一句话标题
- **等级**：P0（直接烧 token / 破坏产物）/ P1（返工）/ P2（体验）
- **触发条件**：什么情况下容易再犯
- **判错信号**：我看到什么就该立刻停下
- **正确做法**：标准动作
- **已犯记录**：日期 · 场景 · 后果
- **状态**
```

## 反例 1 — 把图片级程序化核验结果逐条回显进对话

- **等级**：P0（直接烧 token，且已被用户点名）
- **触发条件**：向用户汇报「某篇论文补了图表」这类结果时，我习惯逐条写出来源 DOI、Zotero Key、
  `verified=True / identity_ok=True / not_blank=True / ink_ratio=0.54…`。
- **判错信号**：回复里出现成行的 `DOI …｜Zotero Key …｜verified=…`，且这些字段在 `figure-completeness.md`
  里已经留过档。
- **正确做法**：对话里只给结论句——「N 张图全部从原 PDF 真实区域提取并程序化核验通过」；
  逐条明细落到 `figure-completeness.md`，需要时用户自己打开。同一批图的 DOI / Zotero Key 只在**首次**
  出现一次，后续用「同上」或直接省略。
- **已犯记录**：2026-10-05 · 补图汇报 · 用户原话「以后这种可以不用写，记到反例模板中」。
- **状态**：待修（已在本次会话生效）

## 反例 2 — 给子代理的 SOP 里写错 CLI 子命令名

- **等级**：P1（直接卡住子代理）
- **触发条件**：派子代理处理单篇论文前，凭记忆写 SOP 命令。
- **判错信号**：子代理报「unknown command」或卡在第一步不动。
- **正确做法**：派发前先核对 `python -m review_workflow.cli --help`（或看 `build_parser` 的 choices），
  并在 SOP 里粘贴核对过的原文。本项目正确命令是 **`attach-note`**，不是 `attach-ai-note`。
- **已犯记录**：2026-10-02 · SYEZQYCB 精读 · 子代理只写完笔记就停住。
- **状态**：已固化（CLI choices 可随时 --help 核对）

## 反例 5 — 批量调 Zotero 插件不重试就判定「不可达」

- **等级**：P1（险些误判环境不可用）
- **触发条件**：顺序高频调用 `zotero.py` 的 `file-url` / `children` 子命令核验一批候选。
- **判错信号**：连续几次返回空，于是写「Zotero 不可达」。
- **正确做法**：先确认 Zotero 进程在跑（`tasklist` / 探 127.0.0.1:23119），再逐篇重试（3 次、间隔 2s）；
  仍失败才判 `blocked_source`。本项目已写 `tmp/robust_verify.py` 兜底。
- **已犯记录**：2026-10-02 · 本批启动前 · 实际 16/17 通过，只是 flaky。
- **补充（2026-10-05）**：反向也会踩——重试后 **0/17 全 FAIL 且报 WinError 10061**（目标计算机积极拒绝）
  时，不要当成 flaky 反复重试，直接查进程/端口：那是 **Zotero 根本没开**。这时 `auto-start-next-batch`
  会报「没有已通过来源核验且达到阈值的候选论文」，正确处置是请用户启动 Zotero，而不是换池子。
- **状态**：已固化（`tmp/robust_verify.py` + 端口探测）

## 反例 6 — 单篇阅读过程中反复做同一套核验（防御性阅读）

- **等级**：P0（直接烧 token，且已被用户点名）——比反例 1 更隐蔽：反例 1 是**汇报时**重复，
  本条是**执行时**重复，每篇重来一遍，200 篇就是 200 遍。
- **触发条件**：处理第 2 篇及以后，仍把第 1 篇那套「裁图 → 读 crop JSON → 数 HTML 里 `<img>` → 算 sha256
  对比 `job.json` → `rebuild-library` → 更新仪表盘 / README / 队列请求」整条流程重跑一次。
  典型动机是「怕上篇没做干净」，即防御性动机。
- **判错信号**：
  1. 同一轮里对**同一份文件**既 grep 又读又算 hash 又重新渲染；
  2. 每篇都 `rebuild-library`、都刷新仪表盘 / README / 队列请求（这些是**共享文件，本来就只能串行、且
     一轮一次**）；
  3. 上一步刚证明过的常量（DOI、Zotero Key、batch id、papers=214）又被查一遍当新信息汇报。
- **正确做法**：**按「一次性 vs 逐篇」分账**（见下面「核验预算表」）。一句话判据：
  *这个结论依赖于「这篇论文」还是「整个流水线」？* 只依赖本篇 → 只在本篇首次产出时验一次，之后
  产物落盘就不再回头；依赖全局（台账、仪表盘、批次门）→ 一轮只做一次，放收尾做。
  产物一旦落盘且没被改动，**不再重复打开它自检第三遍**——自检只在新产物生成时做一次。
- **已犯记录**：2026-10-05 · UGGZ59YD 收尾 · 为确认「图数对了没 / sha256 没动没」，对该篇 HTML 与
  `deep-paper-note.md` 反复 grep / 算 hash；同轮又对 3 篇 human_reviewing 各跑一遍共享台账刷新。
  用户原话「还不要在阅读文献的过程中过多地重复验证、防御性阅读」。
- **状态**：待修（2026-10-05 起按核验预算表执行）

## 核验预算表（反例 6 的执行细则）

判据：结论是依赖**本篇**还是**全局**？依赖全局的，一轮一次，集中到收尾做。

| 动作 | 频率 | 说明 |
|------|------|------|
| PDF 全文抽取 | 每篇一次 | 篇级，无法省，天然一次性 |
| 图表裁切 + 程序化核验 | 每篇一次 | 图本身变了才重跑；图没变只补台账时不重裁 |
| `figure-completeness.md` 写入 | 每篇一次 | 内容自证，写完即终态 |
| HTML 渲染后数 `<img>` / 查缺失标记 | **每篇一次，且只在渲染后** | 不渲染就不数；渲染过且文件没动就不数第二遍 |
| `deep-paper-note.md` sha256 对比 | **每篇一次** | 只在「我动了这份文件」时才需要；**补图/重渲染不算改动**，不必重算 |
| `rebuild-library` | **一轮一次**（收尾） | 共享文件，串行，不逐篇刷 |
| 仪表盘 / `README.md` / `library.json` | **一轮一次**（收尾） | 同上，一轮一个条目 |
| `queue-refresh.request.json` | **状态变化时一次** | 没变就别改 `updated_at`，免得制造假新鲜 |
| DOI / Zotero Key / batch id 之类常量 | 全流水线一次 | 首次出现后直接引用，不再当新信息查证 |

**允许但不必每次做的事**（判错信号出现才做）：
- 上一轮子代理烂尾 → 开工前列一遍 `agent-output/` 清单（反例 3）。
- CLI 子命令名不确定 → `--help` 核对（反例 2）。
- Zotero 返回空 → 重试（反例 5）。

## 反例 7 — 把「人工已提交 json」当成「状态已推进」

- **等级**：P1（用户以为审完了，实际卡在非终态，批次门白锁）
- **触发条件**：用户在评审器里点完八节并「提交更新」之后。
- **判错信号**：`human_reviews/<KEY>.human-review.json` 里 `review_outcome=human_confirmed`、
  `citation_permission.allowed=true` 都在，但 `job.json.state` 仍是 `human_reviewing`。
  ——评审器**只写文件，不推进状态**；推进必须由主代理跑 `import-human-review`。
- **正确做法**：判断终态只看 `job.json.state`，不看 json 是否存在。发现已提交未导入，立即
  `python -m review_workflow.cli import-human-review <那个 json 的路径>`（一次一篇，输出 state=synthesis_eligible）。
- **已犯记录**：2026-10-05 · BKFNNW4J / SYEZQYCB 其实 10-03 就提交完，54XP5895 10-05 01:57 提交，
  但三篇一直停在 `human_reviewing`；用户问「我审完了怎么没进终态」才发现。
- **状态**：待修（无自动巡检，靠每次开工扫一遍 `human_reviews/` 与 `job.json.state` 是否对齐）
